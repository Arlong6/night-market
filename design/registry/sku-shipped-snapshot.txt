# 維護規則
# ─────────────────────────────────────────────────────────────────────────
# 1. 只准「新增列」。既有列一經寫入，永不編輯、永不刪除。
# 2. 維護工具**不應**提供「重新產生」模式。它只讀既有檔、驗證既有列仍可解析、
#    再追加新列。想繞過就必須手改本檔——一個可見、蓄意、可被 review 的動作。
#    （理由：AC15b 若比對名稱會產生假陽性，而解除假陽性的動作「重新產生快照」
#     恰好就是它真陽性的破解法。所以我們比對整數值，並且拿掉那個逃生口。）
#    ⚠ r3 降級：這是**作業慣例**，不是機器閘門。依 GDD 自己的 gate 定義
#    （「gate 的定義性質是 commit 時提交者無法控制它」），一個與資料同 repo、
#    由同一人維護的工具限制是 lint 不是 gate。為它寫一個「反重生」的強制機制，
#    是一個 solo 開發者為防他自己造的機關——成本高於它擋掉的風險。
# 3. sku 列比對的是 machine_family 的**整數值**；名稱欄只是給人看的註解。
# 4. Deprecated 不得回到 Active。
#
# ─────────────────────────────────────────────────────────────────────────
# r3 結構性變更（2026-09-20）：sku 區塊由「狀態快照」改為「事件日誌」
# ─────────────────────────────────────────────────────────────────────────
# 舊格式每列帶一個 status 欄，並要求與現行 SKU 表**雙射**。那組規則在第一次
# 下架時**三路全封死**：
#   - 改那一列的 status → 違反維護規則 1（永不編輯）
#   - 為同一個 sku_id 追加第二列 → 違反雙射（一個 sku_id 兩列）
#   - 什麼都不做 → 快照寫 Active、現行表寫 Deprecated → AC1a 永久紅燈
# 而唯一的出口是「重新產生快照」——維護規則 2 明令禁止的那個動作，
# **而且重新產生會順帶清空宣告層區塊，也就是清掉這個檔唯一活著的那條絆線。**
#
# 改成事件日誌之後，下架**就是**追加一列 DEPRECATED，三個矛盾同時消失。
# 雙射同時降為單向（現行表每筆至少有一列 ADDED）：network_index 永不重用
# 技術上只需對**已出貨**號碼成立，而本檔名為 shipped。把約束提前到 commit
# 邊界，代價是迭代期持續假紅燈——而一條會逼人造出破解法的規則比沒有規則更糟。
#
# 建立日期：2026-09-20（r2 修訂，先建空檔以啟動 AC15a）
# 結構改版：2026-09-20（r3 評審裁決）
# ⚠ r1 原本規定「第一次有 SKU 進 Active 的 PR 才建立本檔」，但那把 tripwire
#   延到 schema 最不穩定的那段時間之後——enum 重排最可能發生在初次內容撰寫期。
#   移到今天的成本是零：一個空檔，之後往下追加。

# 格式：<EnumName>.<MemberName> = <integer>
#       <EnumName>:underlying = <C# 型別>
# 只可附加，不可重排、不可改號、不可刪除、不可改 underlying type。
#
# ⚠ r3 修正：先前這一行是註解，不是可解析的鍵，而 AC15a 的 GIVEN 指名的正是那個鍵
#   ——全文件唯一被宣稱「今天就會亮紅燈」的絆線，指向一個不存在的 referent。
#
# ⚠⚠ 且本檔全文（含本段說明）**刻意不再出現第二次「區塊鍵的字面」**。
#   理由是實測出來的：r3 修訂當下，這段說明自己寫了一次帶冒號的鍵名，
#   於是一個「切在第一個鍵名上」的 parser 會切到註解、拿到空區塊而**靜默通過**。
#   這與同一輪在 AC12b 範本上抓到的 `gate1: PASS` 是**同一個形狀**：
#   **解釋漏洞的文字本身變成了下一個漏洞。** 說明用「區塊鍵」四個字指稱，不寫字面。

#   等於擋住了改號卻沒擋住換型別——同一個攻擊面，換一條管道。
